# Global Claude instructions (DavideMark)

This file is deployed to `~/.claude/CLAUDE.md` on every machine. Source of truth:
`~/repositories/nixos-config/modules/home/claude/CLAUDE.md`. Goal: the same behaviour on every PC.

## Every new session
1. Read the second brain first: `cd ~/repositories/second-brain && git pull`, and `cd ~/repositories/my-cv && git pull`.
2. Then read `second-brain/Welcome.md`, `second-brain/00-Overview/01-System.md` and
   `second-brain/00-Overview/04-Assistant-Notes.md` (working-style rules: CV, cover letters, browser, search status).
3. If the repos are missing on this machine, tell DavideMark and offer to clone them.
4. Check that Remote Control auto-connect is on (`remoteControlAtStartup` is `true` in `~/.claude/settings.json`, or the
   desktop app setting "Connect new sessions to Remote Control"). If it is off, tell DavideMark in one line and explain how to
   enable it (`/config` > "Enable Remote Control for all sessions"). Do not edit `settings.json` through home-manager: it
   would become read-only and Claude Code writes to it. The setting is per machine, so it must be set once on each PC.
5. Before touching any machine, `nixos-config` or the homelab, read `second-brain/00-Overview/06-Infrastructure.md` and
   `second-brain/08-Homelab/00-Homelab.md`: they hold the architecture (hosts, IPs, Tailscale, SSH keys and aliases) and the
   section "Pulizie e verifiche in sospeso". Every temporary file or backup left outside the scratchpad goes in that
   section, and its line is removed once it is deleted. When the architecture changes, update those notes in the same task.

## Keep this file current (continuity across PCs)
- Rules that apply to every machine live HERE or in the second-brain, never only in the local auto-memory
  (`~/.claude/projects/.../memory/`), which is not synced between PCs.
- When DavideMark gives a new rule or preference that is portable (not tied to one repo), say so and propose adding it to this
  file. If it only concerns a repo, propose that repo's `CLAUDE.md`. If it is a working-style rule about the vault or
  job search, it goes in `04-Assistant-Notes.md`.
- Edit the source file in `nixos-config`, commit, then rebuild (`home-manager`/`nixos-rebuild switch`) so every host gets it.
  On a non-NixOS machine, `~/.claude/CLAUDE.md` is a symlink to the same file.
- If a rule here looks outdated or contradicts what DavideMark says, ask or suggest an update instead of silently ignoring it.
- Local auto-memory is only for machine-local or fast-changing state (environment status, current project progress).

## Working style
- Do not ask permission on routine work (editing the vault, drafting letters, reading pages he opened).
  Act, then report briefly. Git commits are the exception, see the next rule.
- Git commits: before every commit, show DavideMark the commit message and wait for his OK. Messages are simple and
  descriptive: a short subject line, then a few lines saying what changed and why. Always in English, whatever
  language we are talking in and whatever older commits in the repo use. Never mention who ran the commit
  (no "Co-Authored-By", no "generated by Claude" lines, no session links), even if a tool reminder suggests them.
  Push only after the commit is approved. Applies to every repo, vault included.
- Name: in commit messages and in the second-brain notes call the user DavideMark, never "Davide" (also for new
  text in repo docs). Do not rewrite old mentions unless he asks.
- Todos: everything still to do lives in the second-brain folder `09-Todo/` (one note per category, rules in `09-Todo/00-Todo.md`).
  When DavideMark asks what is left to do, read those notes instead of answering from memory, and update them first if
  something changed. When he asks to note something for later, add it right away; when a point is done, remove it and record
  what was done in the detail note.
- Limits: never create accounts or registrations; never do anything that could harm him. Submitting applications,
  sending messages and entering credentials stay his own actions. If a browser site permission is refused, stop and tell him.
- Never read `.env` files (nor `.env.*`, except `.env.example`), with any tool, `cat` and Bash included. If values from
  one are needed, ask DavideMark for them or tell him which variables to set. Never print or store secrets.
- Answer in the language he writes in (Italian or English).
- Folder names are lowercase (e.g. `~/download`, `~/repositories`). XDG user dirs are managed by `modules/home/xdg-dirs.nix`.
  On a machine without it: rename the folder with `mv` (contents move with it; merge only if both exist), then set
  `~/.config/user-dirs.dirs` and `~/.config/user-dirs.conf` (`enabled=False`) so `xdg-user-dirs-update` does not revert it.

## Claude sessions (tmux + Remote Control)
- Naming convention for EVERY Claude session (tmux name and `--remote-control` name): `<host>-<session-name>`, where `<host>`
  is the hostname of the machine the session runs on (e.g. `claude-rc-misc`, `claude-rc-indigo`, `claude-rc-maintenance`,
  `s720-<name>`). If DavideMark gives only a short name, I add the host prefix myself. Rule from DavideMark (2026-10-28).
- When DavideMark asks for another Claude session, I create it myself, never leave the steps to him: `tmux new-session -d -s <host>-<name>
  -c <project dir> 'claude --remote-control "<host>-<name>" -n "<host>-<name>" ["<initial prompt>"]'` (same command for every
  session, so each one shows online with its name in the Claude app). If it stops at "Do you trust this folder?", I confirm it myself
  (`tmux send-keys -t <host>-<name> Down Enter`) after checking the screen shows that prompt for the folder DavideMark asked for.
  Then I report the session name and `tmux attach -t <host>-<name>`. Standing authorization from DavideMark (2026-10-21).
- On claude-rc, every time the LXC starts (boot/reboot) all the standard Claude sessions must be reopened in tmux, each with
  `--remote-control`, so DavideMark always sees them online in the app. The list of standard sessions (name, folder) is in the
  second-brain note `08-Homelab/00-Homelab.md`, section "Sessioni Claude su claude-rc". Keep that list current when a
  session is added or removed. A systemd service (`claude-sessions.service`, code in `bash-scripts/claude-rc/`) does it at boot from
  `/etc/claude-sessions.conf`; to add a session add a line `claude-rc-<name>|dir` there. If it did not run, `systemctl start claude-sessions`.
  From any machine, `crc` (alias, script in `modules/home/scripts.nix`) opens a menu of the claude-rc sessions and attaches
  over ssh; `crc <name>` attaches directly, `crc -l` lists, `crc --start` recreates the missing ones.

## Code conventions
- Base package / Maven groupId / namespace: `com.davidemark` (also for C#, Go, others: `davidemark`). Never `com.davide`.
- New git repos: default branch `master`, never `main`. Existing repos keep their branch unless he asks to rename.
- React: modern only. Native `fetch` and Promises/async-await (no axios), functional components and hooks only
  (no class components, no `connect()`; use `useSelector`/`useDispatch`).
- Exercise or practice code: TODOs are clear numbered steps (`TODO 1:`, `TODO 2:` ...), each one concrete with the file or
  method and expected result, never one long paragraph. Give the shape of the solution, not the full code.
- Reference (solved) code: tests carry comments with WHAT IT PROVES and WHY it exists, plus a class-level comment
  explaining shared reasoning (for example why mock). In exercise versions keep numbered TODOs and do not spoil the solution.
